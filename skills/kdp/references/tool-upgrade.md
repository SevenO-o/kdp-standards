# 升级已有工具采用的规范和模板

用户明确要求升级 KDP 工具的规范或模板时读取。本流程随 Skill 安装，独立于维护仓库；不包含公司规范发布或服务器维护操作。当前没有 `upgrade` 或 `migrate` 命令，由 Agent 使用现有助手获取模板后合并代码。

## 确定目标和保存基线

读取原项目 `AGENTS.md`、`kdp.json` 和 `kdp.lock.json`，按 `docs/standards/README.md` 读取原规范；旧包没有 README 时按 Skill 主入口处理。检查工作区现有改动。普通业务修改不自动升级；只安装新版 Skill 也不改变工具版本。

从用户现有公司配置的索引确定目标组合。用户指定组合时采用该组合；明确要求“升级到最新版”时采用当前推荐组合并记录其 ID；只询问升级影响时先比较差异。目标不存在、缺少完整可验证产物或不在服务器支持范围时，说明缺失项，不编造版本、摘要或改变公司来源。

记录原项目绝对路径、原/目标完整组合、需要修改的业务行为及验证项。原工具已经发布时，使用 `status --project` 核对工具 ID、当前发布及升级前可回滚的成功发布。尚未发布的工具不必为升级而登记身份或创建服务器工具。

命令示例中的变量均由 Agent 根据实际环境设置：`KDP_HELPER` 是本 Skill 内 `scripts/kdp.mjs` 的绝对路径，`KDP_PROJECT` 是原项目绝对路径；需要 Node.js 24。先用 `node "$KDP_HELPER" help` 核对命令。

```sh
node "$KDP_HELPER" status --project "$KDP_PROJECT"
```

原工具存在尚未终结的发布尝试时，先查询并解决该尝试，再发起迁移后的发布。普通 `publish` 会先恢复旧尝试，期间改动的代码不会进入其已冻结源码。

为原源码、原锁和必要的本地状态保留可恢复的私有备份，保护未提交的业务改动。优先在原项目路径合并；保留 `.kdp/origin.json`、`.kdp/binding.json` 和项目之外的用户发布记录。凭据不读出、不放入项目或对话。不要删除绑定、换身份或使用 `--new-tool` 解决升级问题。

## 获取对照项目并合并

把 `KDP_TARGET_RELEASE` 设置为已核对的目标组合 ID，`KDP_REFERENCE_PROJECT` 设置为原项目之外、尚不存在的对照项目绝对路径。通过助手下载并校验三类产物：

```sh
node "$KDP_HELPER" init \
  --project "$KDP_REFERENCE_PROJECT" \
  --name "规范升级对照" \
  --description "仅用于合并模板变更，不发布" \
  --release "$KDP_TARGET_RELEASE"
```

初始化会在本机创建项目状态，不登记发布身份或创建服务器工具。不要发布这个对照项目。需要旧模板时，在另一个空目录用原组合 ID 初始化；原组合已撤回且无法取得可信迁移材料时，说明缺少基线，不猜测旧模板内容。

对照“原模板 → 新模板”和“原模板 → 当前业务项目”合并。新模板没有的业务代码并不等于应该删除；按新规则解决冲突，保留功能及已有定制。若新规范要求有重大业务行为选择且上下文不足，先完成无歧义部分，再说明需要用户决定的差异。

先阅读对照项目的 `docs/standards/README.md`，按其入口读取目标规范、条件适用规则和迁移要求。具体技术栈、目录、接口生成、依赖及业务行为的合并要求以目标规范和模板差异为准，不在本说明重复维护。

保留业务代码、依赖和用户定制，按目标规范调整受影响的源码及验证脚本；不得关闭失败检查。规范副本采用经过校验的目标包，并同步项目规则入口。`kdp.json` 保留工具名称、用途和获准能力，只调整新契约要求的字段；`kdp.lock.json` 使用对照项目生成的完整目标锁及摘要，不能只改版本字符串。

不要复制对照项目的 `.kdp/` 或用户级项目记录到原项目。采用目标锁只是迁移的一部分；完成代码合并和验证后才能报告升级结果。

## 检查和按授权发布

在原项目中运行适用的契约生成、业务测试与构建，再执行完整检查：

```sh
node "$KDP_HELPER" check --project "$KDP_PROJECT" --run
```

确认全部检查为 `passed`，`notRun` 不计通过。检查器执行项目脚本，不能代替实际业务验收；验证变更页面的输入、加载、空状态、成功与错误，以及后端受影响请求和响应。说明实际浏览器覆盖范围。

只要求本地升级时，交付修改和检查结果；已发布工具的线上版本保持原发布。已有发布授权时继续，不因进入发布阶段重复请求相同授权：

```sh
node "$KDP_HELPER" publish --project "$KDP_PROJECT" --wait-seconds 120
node "$KDP_HELPER" status --project "$KDP_PROJECT"
```

等待超时不是成功或失败结论；用返回的发布 ID 查询，必要时按助手 `help` 的 `--resume` 恢复同一尝试。服务器 `succeeded` 后，核对工具 ID 保持不变，并访问实际工具入口验证业务。访问方式以适用规范及平台配置为准，管理操作仍须校验所有者。

确实移动了原项目且需要恢复绑定时，先核对原身份和原工具 ID，再按助手支持的 `publish --restore TOOL_ID` 恢复；这是发布操作，仅在发布授权内执行。归属拒绝时不能自动创建替代工具。

## 失败处理与恢复

本地检查失败时修复当前源码；保存原备份，不把失败项目称作升级成功。服务端候选失败时查询实际状态和旧版业务，不能仅凭“部署失败”推断线上已停止。

新版已上线但业务异常时，在回滚授权范围内把 `KDP_PREVIOUS_RELEASE` 设置为该工具升级前已验证的成功发布 ID：

```sh
node "$KDP_HELPER" rollback \
  --project "$KDP_PROJECT" \
  --release "$KDP_PREVIOUS_RELEASE" \
  --wait-seconds 120
node "$KDP_HELPER" status --project "$KDP_PROJECT"
```

查询终态并重新验证真实业务。应用回滚复用历史镜像，不恢复本地源码和版本锁；本地另行恢复匹配的备份，保留后续业务改动。镜像回滚不等于业务数据迁移回滚。

最终报告原/目标组合、合并内容、实际检查与业务验证、是否发布、工具 ID 和发布结果、本地与线上版本是否一致，以及未验证项。不要报告新增了自动迁移命令，也不要暗示一次模板升级会自动更新其他同事的工具。
