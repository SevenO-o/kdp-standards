# 运行环境与依赖兼容规范 v0.1.0

所有工具开发者必读。本页约束所有业务依赖与运行环境的兼容性，涵盖纯 JavaScript、原生扩展、WASM、预编译可执行文件及间接依赖。首次交付、相关依赖变更或运行环境变化时执行适用验收。依赖可安装、类型检查或构建通过，不证明目标服务器可运行。

## 适用问题与最低验证

| 风险类别 | 常见触发 | 至少验证 |
| --- | --- | --- |
| CPU 与二进制平台 | 图片/音视频、压缩、数据库驱动、密码库、推理运行库 | 真实加载扩展或执行文件，执行一次核心运算；核对架构、指令、动态库及 ABI |
| JavaScript 运行时 | 新 Node API、ESM/CJS 差异、条件导出、动态导入 | 在生产 Node 及最终打包形态启动并调用业务入口 |
| WASM 与线程 | SIMD、线程池、共享内存、Worker、编解码/推理模块 | 初始化真实模块并执行运算；线程和资源限制内仍能完成 |
| 随包与系统资源 | PDF、字体、浏览器二进制、模型文件、证书、语言包 | 最终镜像内定位并实际读取必需文件；不依赖开发机缓存或构建时未下载的资源 |
| 安装与构建 | postinstall 下载、平台 optional 包、源码编译、开发依赖被裁剪 | 干净锁文件安装和平台固定无网络构建成功；生产镜像保留必要依赖 |
| 权限与文件系统 | 非 root、只读目录、临时文件、HOME 缓存、子进程 | 按生产用户和路径执行完整业务；写入、清理与失败返回符合平台约束 |
| 资源与生命周期 | 解压/解析扩张、并发编码、推理、线程耗尽、延迟加载 | 最大声明输入及并发内完成，记录峰值与超时；冷启动、首次请求、停止行为可用 |
| 外部服务与协议 | DNS、TLS、代理、数据库/远端 API 的版本或权限 | 将本地处理与外部连接分开验证；mock 通过不能证明真实供应商连通 |

数据库驱动、浏览器或推理库只是风险示例，不代表 KDP 已交付持久数据库、浏览器执行服务、GPU 或任意子进程能力。先核对平台能力边界；不能为了满足依赖要求擅自增加服务、挂载或系统权限。

## 1. 运行基线与证据来源

开发选型按保守基线进行。实际环境由维护者从目标平台和候选容器核实；不能从开发电脑、物理 CPU 型号或依赖的 `linux-x64` 标签推断虚拟机能力。

| 维度 | 开发要求 |
| --- | --- |
| Node.js | 使用锁定模板要求的 Node.js 24；原生扩展还须核对 Node-API/ABI |
| OS、架构、libc | 分别记录目标 Linux、x64/arm64、musl/glibc 及版本；Alpine 的 musl 包与 glibc 包不能互换 |
| CPU | Linux x64 不承诺 SSE4.1、SSE4.2、AVX、AVX2 或 x86-64-v2；仅使用目标虚拟 CPU 已验证支持的二进制 |
| WASM | 不默认承诺 SIMD、线程、共享内存及其他扩展可用；逐一验证所选模块实际需要的特性 |
| 内存、CPU、进程 | 以平台生效的单工具限制验收；当前实现为运行 256 MiB、0.5 CPU、128 个进程/线程配额，仍受共享引擎资源准入约束 |
| 文件、网络 | 非 root、只读根目录、受限临时目录；构建无网络，运行允许外连，但库初始化和离线 smoke test 不得临时下载二进制或编解码文件 |

维护者的验收证据必须带日期、平台版本、基础镜像摘要、Node/libc 版本、架构、虚拟 CPU flags、有效容器限额及 WASM 实测结果。平台变更、迁移或基础镜像更新后复查；过期记录不能当作当前探测。工具开发者无需 SSH，由维护者提供脱敏结果，不分发宿主配置或凭据。

当前助手与发布 API **没有专用的目标 CPU/WASM 兼容性预检命令或端点**。平台支持组合只表示规范组合可受理，不代表每个业务依赖可运行；不能杜撰能力字段或在 `kdp.json` 中加入 CPU、Docker 参数。

增加共享引擎内存不会补齐 CPU 指令集，也不自动提高单工具内存限制。`RESOURCE_CAPACITY_INSUFFICIENT` 与加载错误、`SIGILL`、WASM 编译错误分别诊断，不能统一归因为内存不足。

## 2. 依赖选择与锁定

1. 核对完整依赖树与安装/启动路径，包括 optionalDependencies、平台专用包、`.node`、`.wasm`、随包可执行文件、动态下载资源和安装脚本。检查必需依赖是否误放在开发依赖、锁文件是否遗漏目标平台包。包名检查只能提示风险，不能证明没有原生代码。
2. 按精确版本查阅官方要求，核对目标 OS、架构、libc、CPU 指令、Node ABI 和 WASM 特性。上游未说明时标记未知，用目标环境验证；不能假设“纯 JS 接口”表示底层纯 JS。
3. 依赖走 `package-lock.json`、官方包摘要验证与平台固定离线构建；从干净依赖树验证，不上传开发机的 `node_modules`，不依赖安装脚本联网下载或手动改宿主库。
4. 不兼容时优先采用已验证的纯 JavaScript 或不依赖 SIMD 的 WASM 实现；同样验证资源与业务能力。回退必须在原始故障条件下实际成功，不能仅检查回退分支存在。
5. 从源码编译、替换基础镜像或调整虚拟机 CPU 暴露方式属于维护方案，须另行评估平台构建与运行边界。工具不得以禁用检查、任意宿主命令或联网构建解决。

例如 sharp 的当前 Linux x64 预编译要求包含 SSE4.2，见 [sharp 官方安装说明](https://sharp.pixelplumbing.com/install/)。2026-09-14 的 KDP 目标环境曾同时复现 sharp 0.35.4 原生加载失败及其 WASM 后备模块 `Wasm SIMD unsupported`。这证明 WASM 标签本身不是兼容保证，不表示所有 sharp 版本或所有 WASM 模块都不可用。

## 3. 图片工具可复用的选型与处理边界

以下精确版本组合在 2026-09-14 的目标虚拟 CPU 和 256 MiB 容器内完成过实际图片处理，可作为新图片工具的起点。它是已验证的选型配方，**尚不是模板内置的统一图片模块**；升级其中任何依赖、改变处理链或目标环境都需重新验收。

| 用途 | 依赖与实现 | 验收边界 |
| --- | --- | --- |
| PNG/JPEG/BMP/GIF/TIFF 解码，缩放、裁剪、PNG/JPEG 导出 | `jimp@1.6.1`，使用纯 JavaScript 编解码路径 | 已验静态样例；不据此承诺动画、多页、CMYK、ICC、EXIF 方向与元数据保留 |
| WebP 解码 | `@jsquash/webp@1.5.0`，显式使用包内 `codec/dec/webp_dec.wasm` 基础解码器 | 已验透明静态 WebP；不据此承诺动画或 WebP 编码 |
| 解码前尺寸检查 | `image-size@2.0.2` | 只读头部不能代替完整解码，也不能单独证明文件安全 |

实现时将图片处理集中在工具自身的后端模块：校验格式与尺寸 → 在内存预算内完整解码 → 按业务处理方向和透明度 → 缩放/裁剪 → 编码 → 校验输出尺寸、格式和大小。格式声明只包含实际验收的功能；需要 AVIF、SVG、动画、多页或颜色管理时另补方案和样例，不能宣称与 sharp 全功能等价。

Node 后端必须显式定位并读取锁定包内的 WASM 文件，通过 `init` 的 `wasmBinary` 提供字节，初始化 Promise 复用；用解码后的 RGBA 数据进入 Jimp。不要触发浏览器 URL 的 `fetch` 初始化，不自动选择未经目标验证的 SIMD 编解码器。生产打包后仍须确认 WASM 文件存在并可读取。

透明图转 JPEG 时明确背景色；压缩质量参数不能代替输出体积校验。异常、截断、伪造 MIME 和超限文件必须拒绝，错误不得暴露配置或文件内容。其余输入、下载和临时数据规则见 [文件专项](文件上传与下载规范v0.1.2.md)。

资源预算须按解码像素计算：单份 RGBA 至少约 `宽 × 高 × 4` 字节，还要容纳解码器、编码器、缩放副本、JS 堆与并发任务。不要把 40 MP 等某次工具的上限复制成平台安全默认值；40 MP 单份 RGBA 已约 153 MiB。已验证的合成小输入与并发 1 不证明最大输入/并发可用，必须按工具声明上限补充资源验收或降低限制。

## 4. 最小兼容性验收

首次交付或相关依赖变更时，随源码提供可重复、无需真实密钥或收费服务的最小用例，可放在 `tests/runtime-compatibility.test.ts` 并纳入项目 `npm test`。测试必须调用实际依赖或构建后的业务模块；模拟上游服务可以，不能把待验解析器、编码器、驱动或推理模块 mock 掉。无原生依赖也要验证生产入口与关键路径；确实不适用的类别写明原因，不伪造通过结果。

验收至少覆盖：

1. 冷启动与真实加载，包括动态导入、原生扩展、WASM 初始化和包内资源定位；记录退出码、信号与已脱敏原始原因，不能吞掉错误后返回成功。
2. 执行每项核心能力的最小输入 → 真实处理 → 输出校验：例如音频解码与转码、PDF 含中文字体渲染、压缩包创建与重新解包、数据库驱动加载和协议操作、推理模块初始化与小输入推理。只选择平台已支持且业务使用的能力；不能用 `--version`、`import` 或空响应代替业务运算。图片最少包含透明样例、损坏样例、像素/体积超限样例。
3. 测试声明的最大输入、输出、并发、任务数量和时限；记录容器内存峰值及是否触发 OOM，内存预算必须留出服务本身开销。
4. 在目标服务器候选镜像及实际运行限制下执行，或在经维护者证明 CPU flags、Node/libc、镜像与限额等价的环境执行。开发机通过、只用 `--platform linux/amd64` 构建、较新 CPU 的普通 CI runner 通过都不能替代。
5. 必需模块初始化纳入就绪条件，失败不能返回 ready。不得在每次健康请求中执行完整压力测试或收费请求；平台仍按候选健康后切换入口，旧版本保留原有恢复流程。

当前由维护者在获准的候选验证流程中运行目标用例。普通工具 Agent 不自行提交任意宿主命令，也不为验收直接部署或操作共享服务器。缺少目标执行能力时完成本地工作、提供可运行用例，并将目标验证标记为 `notRun`，说明缺口；不能为得到绿色报告删除用例或把目标结果改成通过。

## 5. 记录、自动化边界与重新验证

工具 README 或自身业务文档应包含下列记录；不得把运行证据写入平台锁、已冻结规范快照或通用 Skill。

| 字段 | 必填内容 |
| --- | --- |
| 依赖 | 直接/间接原生、WASM 依赖的精确版本与所选平台文件；无此类依赖也说明审查范围 |
| 候选 | 封存源码 SHA-256、依赖锁摘要、最终镜像摘要；若测试文件不在镜像内，另记测试摘要与注入方式 |
| 环境 | 日期、平台版本、基础镜像、Node/libc、架构、CPU flags、实际限额与 WASM 结果 |
| 用例 | 可复现入口、真实依赖、格式和输入/并发边界；列明替代了哪些外部服务 |
| 结果 | 分开填写 `local` 与 `targetRuntime`：`passed`、`failed` 或 `notRun`；记录失败原因、退出状态、资源峰值与未覆盖项 |

当前检查器 0.1.10 仅匹配本规范组合，自动范围仍为原有 9 项本地检查。它不会生成上述 `targetRuntime` 字段或验证目标镜像；字段是独立验收记录的约定。检查器显示 passed 不替代目标证据，健康检查也不覆盖所有延迟加载路径。

后续自动化应由平台提供可信环境描述和受控候选执行，将结果绑定源码、依赖锁、最终镜像及环境指纹，再决定兼容性门禁。门禁应对所有工具的关键路径采用同一流程，不能只维护 sharp 或图片库黑名单。由平台控制执行入口、超时与隔离，依赖风险扫描辅助选择用例；未知能力或未运行不能自动记为通过。未实施前不得宣传“自动拦截所有运行兼容问题”。

变更依赖锁、基础镜像、生产打包、业务关键路径、CPU/WASM 能力、资源或权限边界后，原有目标结果失效，重新执行适用用例；任一供应商真实调用未验仍独立列出。规范要求与人工验收用于提前发现问题，不能代替尚未交付的平台自动门禁。
