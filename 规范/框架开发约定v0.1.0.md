# 框架开发约定 v0.1.0

规范包 0.1.14 的唯一必读文档。目标是统一前后端结构，让本地验证覆盖平台路径、网关和生产构建行为，减少部署后才出现的问题。

## 1. 沿用一套框架

前端使用 TypeScript、React、Vite 和模板中的 shadcn/ui 组件；后端使用 Node.js 24、TypeScript、Fastify。生产镜像由一个 HTTP 服务提供静态页面和同源 API。

- `web/` 写页面，沿用 `web/theme.css` 的主题和 `web/components/` 的控件，保持浅深色、键盘及窄屏可用；业务布局自由安排。
- `server/` 写业务与输入校验；从服务端 Schema 生成 `contracts/`，前端使用生成类型，不重复手写两套接口。
- 前端通过 `web/lib/api.ts` 和 `web/lib/http.ts` 调用相对 API 地址，不写死 localhost 或容器地址。
- 沿用 `package-lock.json` 与 `kdp.lock.json`；前者锁业务依赖，后者锁平台组合。业务更新不自动升级规范。

## 2. 用框架承担通用问题

- 成功 JSON 返回 `{ data: ... }`，失败返回 `{ error: { code, message, requestId } }` 和真实状态码。前端使用公共请求模块处理错误与取消。
- 文件调用使用公共下载模块：先校验状态和文件类型，结果大小取实际 `Blob.size`。缺失指标为未知，不能默认显示成 0；模板提供文件选择与下载控件。
- 后端使用模板签名身份适配器；不相信浏览器自报身份。秘密只在后端使用，不进入前端、源码、日志或镜像。
- 页面显示真实的加载、错误和结果；输入变化时标记旧结果，避免重复提交和虚假进度。业务文件、格式、像素、并发及超时由业务按需求校验。

具体参数查 [接口与运行参考](接口与运行参考v0.1.0.md)，无需为浏览器、图片等工具新增独立必读规范。

## 3. 本地按平台方式验证

日常开发运行 `npm run dev`。本地 API 使用与平台共用的网关处理代码，包含响应头筛选、请求头隔离、传输上限和超时。

发布前通过助手执行 `check --run`，依次完成安装、检查、测试、生产构建及平台预览检查。手动查看生产页面时，构建后运行 `npm run preview:platform`，使用输出的 `/tools/local-tool/` 地址；它启用生产静态资源、路径前缀和签名身份。

`npm run verify:platform` 验证该预览中的核心业务。模板带有文本工具样例；修改业务时将此脚本中的成功、错误和结果断言改为实际业务，不删除验证或保留无关样例来凑通过。HTTP 自动验证之外，用浏览器检查实际操作与布局。

本地预览共享 HTTP 行为，但本机进程不等于服务器容器。原生库、WASM、浏览器、字体等依赖，还要在最终镜像和实际目标 CPU、用户、资源限制下验证核心业务；外部服务和网站另验目标网络及登录条件。

## 4. 镜像和配置随工具交付

工具可编辑自己的 Dockerfile，在构建时联网安装业务依赖。保留模板 `build` 阶段供平台独立执行 check/test/build，最终镜像保留全部运行依赖；运行时不临时下载安装二进制。

资源通过平台支持的 `resources.profile` 声明；配置与秘密通过助手同步，后端从环境读取。持久存储、额外服务或宿主权限须有平台实际支持，不能只靠添加声明获得能力。

## 5. 用真实结果交付

发布后从实际平台入口完成一次核心操作，核对输入、页面指标、结果内容和下载文件；再验证一条失败路径。需要浏览器的工具验证真实执行和目标结果，页面能打开或任务接口正常不等于采集成功。

README 简要记录用途、命令、业务限制和验证结果，分别写清本地检查、平台预览与目标服务器是否通过；未测项说明原因。发布、升级已有工具与部署平台按用户授权执行，不把本地通过写成已经上线。
